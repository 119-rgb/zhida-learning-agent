# 售后工作台使用与演示步骤（模块 5）

本文对应页面 `/support.html`，用于演示从「用户提出问题」到「评价关闭」的完整售后流程。**所有账号、产品、订单和知识库内容都是虚构演示数据**，不连接真实支付，不使用任何真实个人资料。

## 一、启动方式

售后工作台需要服务端同时启用售后模块、JWT 和数据库；缺少任意一项时页面会明确提示不可用。

```powershell
$env:ZHIDA_SUPPORT_ENABLED="true"
$env:ZHIDA_AUTH_ENABLED="true"
$env:ZHIDA_PERSISTENCE_ENABLED="true"
$env:DB_URL="jdbc:mysql://127.0.0.1:3306/zhida_agent?characterEncoding=UTF-8&serverTimezone=UTC"
$env:DB_USERNAME="<你的数据库账号>"
$env:DB_PASSWORD="<你的数据库密码>"
$env:ZHIDA_JWT_SECRET="<至少32字节的随机字符串>"
mvn spring-boot:run
```

- 工作台地址：<http://localhost:8080/support.html>
- 研究助手首页会在售后模块启用时显示「售后工作台」入口。
- 不配置 `DEEPSEEK_API_KEY` 时，售后助手的对话处于演示模式，只能说明未调用模型；工单、订单和知识库功能不受影响。

## 二、准备演示账号（一次性）

注册接口只能得到 `USER` 角色。客服和管理员必须在数据库里显式配置，这是刻意的设计：接口不接受客户端提交的角色。

```sql
-- 注册三个账号后（用户名任意，这里用示例名），在数据库里提升角色：
INSERT INTO support_account_role(user_id, role)
SELECT id, 'ADMIN' FROM user_account WHERE username = 'zhida_admin';

INSERT INTO support_account_role(user_id, role)
SELECT id, 'CUSTOMER_SERVICE' FROM user_account WHERE username IN ('zhida_agent_1', 'zhida_agent_2');
```

### 可选：用演示数据开关一键准备（推荐用于可重复演示）

也可以让应用自己准备一套固定的虚构演示数据，避免手工建账号和造单。它默认关闭，必须同时打开两个开关并提供临时密码：

```powershell
$env:ZHIDA_SUPPORT_ENABLED="true"
$env:ZHIDA_SUPPORT_DEMO_DATA_ENABLED="true"
$env:ZHIDA_SUPPORT_DEMO_DATA_PASSWORD="<8 到 64 位的临时演示密码>"
```

启动后会幂等创建三个虚构账号（`zhida_demo_user` / `zhida_demo_agent` / `zhida_demo_admin`）、一个分类 `虚构订阅开通问题`、一个产品 `DEMO-SUB-PRO` 和一张「已付款未开通」订单；重复启动不会重复创建。

两条安全约束（行为已实现，负向用例的覆盖情况见下）：

- 密码只从环境变量读取，长度不合法会直接启动失败，不会写入任何文件或日志。
- 如果库中已存在同名但**非本配置创建**的账号，或演示账号的角色被手工改过，应用会停止启动并提示改用独立演示数据库；它不会接管、改名或提权已有账号。

对应自动测试：`SupportDemoDataConfigurationTest` 覆盖正常初始化与重复执行幂等，并覆盖密码不合法、同名非演示账号、演示账号 ID 被占用、演示账号角色被改这四条安全停止分支；停止时都会断言已有账号与角色记录未被修改。

> 属性名是 `zhida.support.demo-data.password`（环境变量 `ZHIDA_SUPPORT_DEMO_DATA_PASSWORD`）。
> 写成 `ZHIDA_SUPPORT_DEMO_PASSWORD` 不会被识别，应用会因密码校验失败而拒绝启动。

## 二之二、浏览器自动验收

`scripts/verify-support-workbench.cjs` 用 Playwright 对一个显式启用 demo-data 的隔离实例跑完整闭环（用户订单 → 结构化出处 → 长草稿确认 → 客服接单/回复/方案 → 用户退回 → 客服再方案 → 用户关闭评价 → 手动建单 → 管理端公共知识库）。

```powershell
$env:ZHIDA_BROWSER_BASE_URL="http://127.0.0.1:18080"
$env:ZHIDA_SUPPORT_DEMO_PASSWORD="<与 demo-data 相同的临时密码>"
$env:PLAYWRIGHT_MODULE_PATH="<本机 playwright 包路径>"
node scripts/verify-support-workbench.cjs
```

- 脚本不写截图、Token、密码或日志文件，只把断言结果打到标准输出；`PLAYWRIGHT_MODULE_PATH` 是本机绝对路径，只用于运行，不写入仓库。
- 助手回答使用脚本内构造的 SSE 事件回放，不调用真实模型；因此它验证的**页面**如何处理出处卡片、依据不足提示和长草稿。回放不能证明后端仍会发出这些事件，所以脚本另外用 `assertAssistantStreamContract` 直接请求真实接口校验 SSE 事件契约（Demo 模式无需模型）。
- 脚本用「后端真实状态」判定状态流转（轮询详情接口），而不是靠页面文案，避免把历史事件里的文字误当成当前状态。
- 打开工单详情必须用整页重载：`page.goto()` 到只差 hash 的同文档 URL 不会重新加载文档，SPA 不会重新初始化，页面会停留在上一次（可能过期）的渲染结果。
- 详情操作走 `actOnTicket`：先确认后端状态，再打开详情并重试按钮，避免把偶发的渲染抖动误报成功能缺陷。

## 三、演示步骤（约 5 分钟）

### 1. 管理员准备演示数据

用管理员账号登录 `/support.html`。

1. 侧栏「分类管理」→ 新建分类，例如 `虚构订阅开通问题`。
2. 侧栏「产品与订单」→ 录入产品（SKU 例如 `DEMO-SUB-PRO`）。
3. 同页「录入演示订单」：选择用户、产品，付款状态 `PAID`、开通状态 `NOT_ACTIVATED`。
   - 也可以再建两张，分别验证 `PENDING_PAYMENT + NOT_ACTIVATED` 和 `PAID + ACTIVATED` 两个场景。
   - 故意选择 `PENDING_PAYMENT + ACTIVATED` 会被服务端拒绝（400），这正是「待付款不可能已开通」的业务约束。

### 2. 用户用售后助手描述问题

用普通用户账号登录。

1. 侧栏「售后助手」→ 输入 `我的订单已经付款，但服务没有开通`。
2. 观察过程提示：助手会依次调用「查询我的订单」「检索售后资料」等工具，回答里会引用真实订单号和状态。
3. 如果公共知识库还没有上传资料，助手会明确说明**资料不足**，而不会编造开通时限或承诺退款。

> 若要演示「有依据的回答」：先用管理员账号在「知识库」页把 `docs/demo/fictional-product-support.md` 上传到公共库 `product-support`，等待状态变为「已就绪」，再重复本步骤。助手回答时会引用文件名与页码/片段编号。

### 3. 确认后创建工单

1. 助手整理出草稿时，页面弹出「确认创建工单」，展示标题、分类、问题描述和关联订单。
2. 此时**还没有工单**：草稿只是待确认内容，没有写入数据库。
3. 点击「确认创建工单」→ 页面先按草稿的 `requestId` 检查是否已建单，然后以 `confirmed=true` 提交；成功后直接跳转到工单详情。
4. 重复点击或刷新后再次确认，不会产生第二张工单（幂等）。
5. 点「暂不创建」只是收起弹窗，草稿仍保留，可用输入框下方的「查看草稿」重新打开；只有确认建单才会写库。

### 3b. 自己生成草稿（不依赖模型）

真实模型并不总会主动调用草稿工具，所以助手页在输入框下方提供「生成工单草稿」入口，不必等模型给草稿：

1. 先描述问题并等助手回答完（描述会带入本轮问答；若还没对话，则取输入框里已写的内容）。
2. 点「生成工单草稿」→ 展开表单：分类和「关联订单」下拉都来自服务端接口，不需要手输 ID。
3. 可修改问题描述后提交。后端会走与模型工具**同一个**校验与 requestId 生成逻辑，并固定返回 `confirmed=false`、不写数据库。
4. 随后弹出同一个确认弹窗，用户确认后才建单。这条链路同样受「分类必须启用」「订单必须属于本人」「requestId 幂等」约束。

### 4. 客服接单并提交方案

用客服账号登录（可以同时开两个客服账号演示并发）。

1. 侧栏「待受理队列」→ 打开工单 → 「接单处理」，状态变为**处理中**。
2. 在「回复用户」里说明排查进度，在「提交解决方案」里写明处理动作，状态变为**待用户确认**。
3. 并发演示：两个客服账号同时打开同一张待受理工单并点击接单，只有一个成功；另一个会得到「工单已被接单」或「无权查看」的提示，页面自动刷新为最新状态。

### 5. 用户确认或退回

1. 用户打开工单详情，在「方案是否解决了问题？」里选择：
   - 填写评价分数与内容 → 「确认解决并关闭」→ 状态变为**已关闭**；
   - 或点「仍未解决，退回处理」→ 状态回到**处理中**，客服可继续处理。

### 6. 核对状态流转与审计

工单详情右侧的**状态脊线**显示当前处于四态流程的哪一步；下方「状态变更记录」列出每一次变更的操作人、角色、前后状态和时间。演示时可以对照确认：

```
v0 CREATED  用户 → 待受理
v1 CLAIM    客服 → 处理中
v2 REPLY    客服 → 处理中
v3 SOLUTION 客服 → 待用户确认
v4 REOPEN   用户 → 处理中
v5 SOLUTION 客服 → 待用户确认
v6 CONFIRM  用户 → 已关闭
```

每次成功变更都会让版本号加一，并且业务记录与审计事件在同一事务里提交；所以「状态变更记录」与工单当前状态永远一致。

## 四、权限边界（答辩时可演示的拒绝场景）

| 场景 | 预期结果 |
| --- | --- |
| 用户访问客服工单详情 | 404（与不存在同样处理，避免探测） |
| 用户调用接单、提交方案 | 403 |
| 客服查看「待受理队列」以外的他人工单 | 404 |
| 普通用户访问分类管理接口 | 403 |
| 游客登录后进入售后工作台 | 403，页面提示游客不能使用售后模块 |
| 用户 B 打开用户 A 的订单或工单 | 404 |
| 两个客服同时接单 | 只有一个成功 |
| 用旧版本号提交变更 | 409，页面提示已刷新 |
| 同一 `requestId` 换内容重复建单 | 409 |
| 管理员替用户确认关闭 | 没有这个入口，服务端也不存在该路径 |

## 五、当前限制

- 售后工作台是**演示级页面**：没有做多语言、主题、虚拟滚动和前端单元测试；工单列表上限沿用后端的 100 条。
- 知识库上传后的解析、分块和向量化是异步的；未配置 Embedding 服务时文档会停留或失败，检索会明确返回「依据不足」。
  - 文档处于「处理中/删除中」时页面会自动轮询刷新状态（只更新文档区，不整页重载），完成后自动停止；轮询总时长上限 2 分钟，超过后提示手动刷新。切换路由或退出登录会立即停止轮询。
- 售后助手目前只面向当前账号自己的订单与工单；客服和管理员的 AI 辅助尚未实现。
- 页面隐藏按钮只是体验优化，**权限判断始终在服务端**；接口被直接调用时同样会被拒绝。
- 浏览器验收目前只用 Chromium；跨浏览器与移动端未验收。页面用例也还没有纳入 `mvn test`。

## 六、本轮修复的页面缺陷（2026-09-17）

| 缺陷 | 现象 | 修复 |
| --- | --- | --- |
| 长草稿弹窗无法确认 | 问题描述接近 4000 字时，确认按钮被挤出视口且弹窗不能滚动，用户点不到「确认创建工单」 | `.auth-dialog.wide` 增加 `max-height: calc(100dvh - 48px)` 与 `overflow-y: auto`，弹窗内部可滚动 |
| 详情渲染过期状态 | 页面初始化与 hash 跳转会并发调用 `dispatch()`，较早发起的那次可能后返回并覆盖新页面，导致详情显示旧状态（例如仍显示「待受理」） | `dispatch()` 增加渲染序号 `dispatchToken`，只有最新一次允许写视图；过期结果直接丢弃 |
| 浏览器脚本误判 | 脚本用页面文字（`getByText('待用户确认')`）判定状态流转，可能匹配到历史事件文字而误判通过；`page.goto()` 到同文档 hash 不重载 | 状态断言改为轮询后端详情接口；打开详情改用整页 `reload`；操作按钮改为显式等待可交互并输出面板内容便于定位 |
| 后端事件无覆盖 | 页面用例回放自造 SSE，后端即使不再发出 `support.ticket-draft.ready` 也照样通过 | 增加 `assertAssistantStreamContract`：直接请求售后助手接口（Demo 模式不调模型），断言响应是合法 SSE 且事件序列完整 |
| 渲染抖动误报 | 偶发页面渲染未完成时单次等待超时，但后端状态其实已正确 | `actOnTicket` 先确认后端状态，再打开详情重试若干次；重试前重新确认状态，避免掩盖真实冲突 |
