## 关键设计

| 设计点 | 依据 |
| --- | --- |
| 调用模式由服务端固定 | 客户端在请求体中声明模式就可以挑选更宽松的指令与工具集，因此模式来自入口而非请求 |
| 售后独立系统指令 | 研究助手指令允许联网搜索、面向通用研究问题；售后必须只基于本系统订单、工单和授权知识库回答 |
| 售后独立工具集 | 只有查询 + 草稿；没有 create/close/refund/payment/activate/assign/claim，模型无法通过任何工具改变业务状态 |
| 工具不接受身份参数 | 身份只从服务端认证上下文写入的 `SupportToolContext` 读取，模型伪造 `userId` 无效 |
| 草稿与建单分离 | 草稿不写库且 `confirmed=false`；建单仍走 `POST /api/v1/support/tickets` 并在事务内重新校验分类、订单归属与 requestId 幂等 |
| 防重复查询接口 | `GET /api/v1/support/ticket-drafts/{requestId}` 返回 204/200，仅作用于当前用户，降低重复提交风险；最终防重复依靠唯一约束 |
| 失败降级 | 模型/供应商失败只结束本次 SSE 会话；工单接口不依赖模型 |
| 共享 SSE 传输 | 研究与售后共用 `ResearchSseStreamer`，取消、超时、事件编号和队列保护只有一份实现 |

| 问题 | 修复 |
| --- | --- |
| `ResponseEntity.of(Optional.empty())` 返回 404 | 会把「尚未建单」误报为「资源不存在」，改为显式映射 200/204 |
