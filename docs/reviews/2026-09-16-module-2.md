## 审查范围

独立只读审查虚构产品、模拟订单、订单归属查询、工单订单关联、模块 1 旧表升级、DDL、HTTP/Service 测试、中文注释和文档声明。重点核对角色与 owner、合法订单状态、幂等并发、业务/审计事务，以及是否存在修改付款或开通状态的入口。

## 结论与修复

首次审查未发现 P0–P2 问题，确认：

- 订单本人列表和详情查询把 `user_id` 放入 SQL；跨用户读取及跨用户关联工单均返回 404。
- 管理员造单以 `(created_by, request_id)` 唯一约束裁决并发重试，订单/产品与 CREATED 审计同事务提交。
- 三个合法状态组合由 Service 和数据库 CHECK 双重限制；待付款已开通被拒绝。
- HTTP 和 Service 均没有修改既有订单付款、退款或开通状态的方法；模块 4 仍须只注册查询工具。
- 工单在创建事务中按 JWT 用户再次校验订单归属，`orderId` 进入工单幂等摘要。

审查提出 3 项 P3，均已修复并复查通过：

| 问题 | 修复与复查 |
| --- | --- |
| 类注释把未来 Agent 只读边界写得像当前类型已经保证 | 改为明确“当前没有既有订单状态更新方法”，并注明模块 4 工具注册仍需只选择查询方法；复查通过 |
| 订单审计回滚已覆盖，产品创建审计失败未单独覆盖 | 增加 H2 触发器故障测试，验证 product_event 写失败时产品本体回滚；复查通过 |
| 未显式覆盖客服、游客的产品/订单接口权限 | 增加真实 JWT/HTTP 断言：客服造单和查本人订单均 403，游客查订单 403；复查通过 |

修复范围重新执行 `ProductOrderServiceTest` 与 `SupportOrderHttpTest` 共 8 项，0 失败、0 错误、0 跳过。最终独立复查未发现新问题。

## 保留边界

- 自动测试使用 H2 MySQL 模式；真实 MySQL 的 JDBC 元数据识别、`ALTER TABLE`、外键和索引 DDL 尚未执行。
- 启动期 DDL 仍按单实例设计，不宣称多实例同时迁移安全；订单列表最多 100 条，尚无分页。
- 当前管理员接口只创建虚构初始状态，不连接真实支付或开通系统；没有订单状态流转接口。
- 模块 2 尚未提供 LangChain4j 订单工具、页面或真实模型验收，这些属于后续模块。

审查结论：模块 2 通过独立审查、修复复查和隔离自动验证；真实 MySQL 未验收是已记录的非阻断边界。
