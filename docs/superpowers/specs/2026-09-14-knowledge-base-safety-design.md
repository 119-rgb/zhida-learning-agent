# 知识库访问与删除一致性设计

## 目标

本次改动只处理 review 中优先级最高的两个问题：

1. 持久化模式下，自定义知识库必须真实存在且属于当前用户，不能通过随意构造路径 ID 绕过每库文档数量限制。
2. 文档删除即使在向量、原文件或目录保存任一步失败，也必须保持可识别、可重试的状态，服务重启后能够继续清理。

不在本次范围内的内容包括任务详情接口聚合、整个 `KnowledgeBaseService` 拆分、Agent 工具上下文机制替换和任务状态枚举化。

## 访问边界

新增 `KnowledgeBaseRepository`，集中保存、列出和检查用户创建的知识库。`KnowledgeCollectionController` 不再直接执行 SQL。

新增 `KnowledgeBaseAccessService`，提供唯一的知识库解析入口：

- 未传 ID 时使用 `default`。
- 校验 ID 格式和长度，与数据库 `VARCHAR(50)` 保持一致。
- `default` 始终可用。
- 未启用持久化时保留当前本地开发行为，允许合法的临时知识库 ID。
- 启用持久化时，自定义 ID 必须由当前 owner 创建，否则返回 404。
- 校验通过后才生成内部向量命名空间；认证模式仍使用 owner 与知识库 ID 的哈希隔离。

`KnowledgeController` 和 `ResearchOrchestrator` 都复用该服务，避免文档接口已经校验、Agent 查询链路却绕过校验。

## 删除状态机

`DocumentStatus` 新增 `DELETING`。删除流程调整为：

1. 在内存目录中把文档从 `READY` 或 `FAILED` 改为 `DELETING`，并先持久化 `catalog.json`。
2. 幂等删除向量数据。
3. 使用 `deleteIfExists` 幂等删除原文件和文档目录。
4. 物理清理全部成功后，从目录移除记录并再次保存目录。

如果第 2～4 步失败，目录记录保持 `DELETING`。再次调用删除接口会继续清理，而不是恢复为 `READY`。服务启动读取目录时，会把遗留的 `DELETING` 文档提交到已有的知识库后台执行器继续删除。`PROCESSING` 的原有恢复规则不变，重启后仍转为 `FAILED`。

删除中的文档不参与检索，也不能重试索引；前端状态文本显示“删除中”。

## 注释原则

代码注释解释不可从语句直接看出的约束：为什么必须先持久化 `DELETING`、为什么本地非持久化模式允许临时 ID、为什么自定义知识库必须经过 owner 校验。普通 getter、构造器和显而易见的流程不添加逐行注释。

## 测试

采用测试先行：

- 持久化模式下访问不存在的自定义知识库返回 404。
- 用户创建知识库后可以正常访问其文档列表。
- 不同用户不能借用相同自定义知识库 ID。
- 删除过程中向量或文件清理失败时，目录状态保持 `DELETING`，再次调用可完成删除。
- 重启读取到 `DELETING` 时会安排继续清理。
- 原有文档异步处理、失败重试、PDF 解析、鉴权隔离和默认启动测试继续通过。

验收执行目标测试后，再运行完整 `mvn test`。真实 MySQL 测试仍保持显式开启，不在默认测试中连接本机数据库。
